# 模块四开发与验收

依据《南邮-实施方案》4.1.1.4、4.2.3 和第 7 节推进。组件逻辑、容器运行单元、处理资源分别建模，以组件到实例、实例到处理资源两层映射连接。

## 开发顺序

| 阶段 | 范围 | 状态 |
| --- | --- | --- |
| 一 | 全局池、两层映射、物理资源账本、独占租约、重置归还、Warm 复用 | 已实现 |
| 二 | Active 整批排队复用、时限回退、动作选择与开销评价 | 已实现 |
| 三 | 四类事件、等待优先级调整、帧边界局部重绑定及回滚 | 软件仿真已实现 |
| 四 | 兼容 Linux 下的真实快照恢复、冷启动/Warm/Restore 对比实验 | 已实现，实际环境与结果见下文 |

完整策略为 Active → Warm → Restore → Cold，均须满足功能、时限和容量约束。Restore 仅在配置真实 Docker 快照库后参与选择；软件仿真不生成快照。单容器装载多个组件的策略尚未实现。

## 第一阶段运行约定

`DeploymentManager` 持有一个 `GlobalContainerPool`，同一管理器下所有任务共享。启用持久化后支持单一管理进程的退出接管；文件锁拒绝同一日志的第二个同时管理者。多副本分布式协调仍未实现，多个独立池不能共同管理同一硬件预算。

生命周期为 Cold、Active、Warm、Release。Cold 对应镜像或组件模板，不伪造运行实例；其余状态对应实例。CREATING、LEASED、RUNNING、RESETTING、READY、QUARANTINED 是辅助操作阶段。

实例使用独立 `pool-UUID`，每次借用产生新租约。组件节点绑定实例，实例绑定处理节点及核心/区域；完成后解除任务绑定，Warm 保留资源绑定。同 CID、实现、版本、参数、端口契约、处理位置和资源规格才可复用。Docker 按镜像 ID 固定版本；仿真保留 Python 工作环境，归还及再次借用时重新构造组件，避免滤波历史、相位、缓存、统计跨任务污染。同一任务的多帧仍保留连续状态。

资源唯一账本为 `TaskScheduler` 的物理放置状态。模块三的共同判别器只对实际选中的 Warm 实例抵扣常驻占用；提交时原子地转换为活动方案占用。CPU 保留内存、DSP 保留本地存储、FPGA 保留 LUT/FF/DSP48/BRAM；链路按活动任务计入。任务预留结算不表示 Warm 资源归零。

Warm 默认最多 8 个，闲置阈值 60 秒。提交前清理过期项；容量不足时按最近使用时间淘汰空闲项；归还后检查数量上限。TTL 由操作触发，也可显式调用维护接口，没有后台定时销毁。确认销毁后才释放资源；失败则隔离并保留预算，可重试清理。启动和底层销毁同时失败时，须先核对实际运行对象，不自动宣布资源释放。

当前按整批任务独占执行，支持任务结束后的 Active 排队交接，不交错执行不同任务的数据帧。先统一预留任务全部组件，再执行创建、检查和重置；阻塞运行调用不持有全局调度锁。Release 诊断历史最多 64 条。正常服务退出先等待异步任务；启用 Docker 持久化时保留 Warm 供接管，其他情况销毁空闲池。

第二阶段将实例准备成本纳入模块三共用的可行性与代价检查。DSP/FPGA 为软件模型，实际处理仍消耗宿主 CPU/内存；专用预算不等于宿主开销监测。

## 第二阶段的整批排队策略

用户选择按任务排队。一个任务的全部帧完成后，重置实例，再交给下一个任务。正在执行的上下文不会被另一个任务覆盖；每次实际交接仍产生新租约。仿真后端按实例加锁，其他独立实例的参考计算可继续运行，不再持有贯穿信号处理的全局运行锁。

新任务先检查兼容的 Active 实例能否在剩余时限内完成等待、准备和执行，再检查 Warm 和冷启动。允许方案混用复用实例和新实例。Active 候选以一个前序任务为等待对象，可复用它的部分或全部组件；当前不尝试合并多个前序任务的运行实例。每个动作都调用现有 Exact、Chain DP 或 HEFT 进行资源放置，并重新验证容量与时限，不绕过模块三。

当前以兼容实例为搜索锚点，最多检查 16 个复用候选，并保留一次冷启动回退搜索。一次动作评价共享 `max_assignments` 搜索预算。优先级为 Active、Warm、Restore、Cold，同层比较预计总耗时；这是有界策略，不声明整个运行调度全局最优。计划中的 `optimality_proven` 因而置 false。不同图和未被枚举的候选可能存在其他可行方案。

等待队列默认最多 16 个任务，最长等待 5 秒，实际还受任务剩余时限减去自身预计执行时间限制。按共享目标实例的入队顺序交接，不依赖线程唤醒顺序。等待只登记目标，不增加活动资源预留、不取得执行租约；原任务仍拥有资源。已被排队任务认领的 Warm 实例不能手工释放或被 TTL/数量淘汰；8 个 Warm 的保留上限针对未被认领的空闲项。前序任务归还后，再原子地取得整批资源与新租约，避免任务各持部分资源相互等待。

估计等待包含前序任务尚未完成的整帧工作、归还准备以及前方重叠排队任务的工作量；当前帧按完整一帧计入，不把已经耗掉的墙钟时间视为必然进展。候选搜索实际消耗的时间也从剩余时限扣除，避免搜索完成后采用已经超时的方案。条件变量按实际归还通知唤醒，等待期间释放全局调度锁。实际等待达到预算、前序任务失败、实例被隔离或资源条件变化时，取消目标认领，扣除实际等待时间，重新选择 Warm 或 Cold；仍无可行方案时明确拒绝，不无限排队，也不抢占原任务。

实例准备估算优先使用同版本、实现、处理位置和精确配置的近期成功动作最大观测值；缺少样本时使用画像初始化成本。Warm/Active 缺少专门观测时可使用归还重置加健康检查的历史最大值。动作统计最多保留 256 组、每组 64 次样本。这些观测不是统计 p95，也不提供硬实时保证；与合成运行画像组合时，在 `dispatch.cost_note` 中标注来源。

方案的 `dispatch` 包含候选判定、预计等待/准备/总耗时、实际排队时间、逐节点实际准备和清理耗时；`allocations[].acquisition` 区分 active_reuse、warm_reuse、cold_start。`GET /api/v1/pool` 增加 pending_tasks、每实例 queue_depth 和 action_costs。排队时实例的 task_id 仍属于正在执行的任务，不能将等待登记误读为已获得硬件资源。

不支持同时拥有多个任务上下文或帧内抢占。第三阶段支持下述软件参考运行单元的帧边界重绑定，真实 Docker 快照恢复属于第四阶段。

## 第三阶段动态调度

新任务进入执行管理器时自动发出 new_task；priority_change 更新活动/等待任务优先级并重排等待认领，不能打断正在执行的任务。每个完整帧后，以剩余帧的画像耗时与实际剩余墙钟时限比较，自动产生一次 deadline_risk。resource_load 接收节点利用率遥测，达到 0.85 将该节点列为避让位置；低于阈值的后续事件可解除避让。遥测值不修改硬件容量或已有背景预算，不等于实际硬件采集。

事件在下一完整帧边界合并处理，每个边界最多修改一个组件。高负载事件优先选择受影响组件；其他事件选择当前处理耗时最大的组件，只有预计收益超过重新绑定准备成本才调整。其余组件的处理位置、实现和资源需求必须保持一致。沿用模块三的容量、链路、接口画像和时限检查，未找到可行目标时保留原方案。该策略是局部启发式，不声明全局最优，不进行帧内抢占。

当前 SoftwareSimulationRuntime 在安全边界保留原 Python 组件对象，原子更新资源位置和画像，滤波状态、相位、缓存与消息重组状态不重置。保持实例 ID 和本任务租约，更新唯一资源账本、池记录及运行绑定；提交失败会恢复运行绑定和账本。此操作是逻辑仿真重绑定，不是复制实际 DSP/FPGA 状态、Docker 迁移或 CRIU 检查点。其他后端缺少状态转移接口时明确跳过调整，继续原任务。

`GET /api/v1/dynamic` 返回阈值、遥测、运行任务及最近 256 条事件/动作。`POST /api/v1/dynamic/events` 接受以下字段：

```json
{"event":"resource_load","processing_node_id":"xc7k410t-region-1","utilization":0.95}
```

其他事件为 `{event:priority_change, task_id:运行任务ID, priority:0到100整数}`、`{event:deadline_risk, task_id:运行任务ID}`、`{event:new_task, source_task_id:新任务ID}`。后者仅模拟到达通知，不会自动创建虚构任务。未知字段、未知节点及无效利用率会拒绝。运行任务完成后不会重放其未处理事件。

资源页新增事件注入及调度记录面板。执行进度包含 dynamic_event、rebound、rebind_skipped；最终计划 dispatch.rebindings 保存原位置、新位置、触发原因及剩余帧数。短任务可能在手工发送前已结束，可用确定性演示 `python -m examples.dynamic_rebinding_demo` 在第一帧后注入全部四类事件，输出 `outputs/dynamic-rebinding-demo.json`。没有人为延长处理时间。

`python -m unittest tests.test_dynamic_scheduler -v` 验证输出一致性、单组件局部性、转移和提交失败回滚、无目标保留原方案、优先级重排及 API 校验。完整联合验证运行 `python -m unittest discover -s tests -q`。

## 接口与页面

- 同步和异步执行均接受布尔字段 `keep_warm`；缺省 false 保留结束销毁行为，显式 true 启用池化。
- `POST /api/v1/plans?keep_warm=true` 使用 Warm 抵扣只读预览，不借用、不释放实例；提交重新规划。
- `GET /api/v1/pool` 查询实例、租约与两层映射。
- `POST /api/v1/pool/maintenance` 执行过期与数量维护。
- `POST /api/v1/pool/instances/{instance_id}/release` 释放空闲实例，拒绝活动实例。
- `POST /api/v1/pool/tasks/{task_id}/retry-cleanup` 重试隔离任务清理。
- 工作台默认勾选 Warm 保留。执行表显示冷启动/Warm 复用与实例 ID；资源页显示状态、阶段、复用次数、两层映射及空闲释放操作。
- 工作台“并发提交两次”使用两个不同任务 ID，展示真实的 Active/Warm/Cold 选择和两份执行结果；详细链路显示最后提交的任务。短任务可能直接命中 Warm，不人为延长处理时间。

Docker worker 新增 `/reset`，保留容器并重新构造组件。旧镜像须重建；无法安全重置的实例销毁。Docker 后端仍仅支持 CPU，DSP/FPGA 是进程内仿真实例，其状态不属于真实硬件快照。

## 验收

`python -m unittest tests.test_container_pool -v` 覆盖跨任务复用、独立租约、输出一致性、满容量抵扣、三种算法、并发独占、失败清理、隔离重试、过期淘汰及 API。HTTP 测试需要本机回环网络。

`python -m examples.container_pool_demo` 将两次四帧任务的编号、租约、分配和 Warm 复用结果保存至 `outputs/container-pool-demo.json`。输入和画像为合成数据，不能代替真实 Docker 或 Linux 快照实验。

`python -m unittest tests.test_active_pool -v` 检查 Active 交接、FIFO、重复任务拒绝、实际与预计等待回退、状态隔离、前序失败恢复、认领保护、独立实例并行和 HTTP 进度/成本数据。

`python -m examples.active_pool_demo` 并发提交两个 128 帧合成任务，将实际动作与成本保存至 `outputs/active-pool-demo.json`。未添加处理延迟；若运行过快，也可能选择 Warm。该样例验证调度行为，不是硬件速度基准。
